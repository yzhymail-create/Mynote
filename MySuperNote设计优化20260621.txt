# 个人日记 App 需求与终局方案总结

## 一、项目目标

开发一个长期使用（10~30年以上）的个人日记 App，满足以下核心需求：

### 1. 数据永久保存

用户希望：

* 日记写几十年都不会丢失
* 手机损坏后可完整恢复
* 更换手机可迁移
* 备份文件能够长期保存

因此需要：

```text
导出
↓
保存
↓
重新导入
↓
100%恢复
```

包括：

* 日记内容
* 时间
* 标签
* UUID
* 图片
* PDF
* 录音
* 其它附件

全部保留。

---

### 2. 数据量越来越大仍保持流畅

假设：

```text
每天1篇
30年
≈ 10000篇日记
```

再加附件：

```text
图片
PDF
录音
视频
```

数据量可能达到：

```text
几十GB ~ 数百GB
```

要求：

* 手机启动快
* 搜索快
* 标签筛选快
* 日历浏览快

不能因为历史数据过多而变卡。

---

### 3. 历史内容可长期查阅

例如：

```text
2026年
↓
想查看2010年的日记
```

要求：

* 可以查看
* 可以搜索
* 可以筛选标签

但不希望：

```text
把全部历史数据重新导入数据库
```

否则：

* 容易污染当前数据库
* 容易产生重复数据
* 操作复杂

---

### 4. 专题内容独立导出

例如：

```text
#专利
#工作
#钓鱼
#学习
```

希望能够：

```text
只导出专利相关内容
```

形成：

```text
专利知识库
```

或者：

```text
只导出钓鱼日记
```

形成：

```text
钓鱼记录集
```

而不是导出全部日记。

---

### 5. 导出文件电脑可直接阅读

即使没有安装 App：

```text
Windows
Mac
Linux
```

也能查看。

例如：

```text
Markdown
JSON
```

能够直接打开阅读。

---

# 二、终局架构方案

## 数据库层

采用：

```text
SQLite
```

仅保留两张核心表：

```sql
diary
diary_archive_index
```

---

### diary

存放：

```text
近5年活跃数据
```

例如：

```text
2022~2026
```

所有日常功能只操作这一张表。

包含：

```text
uuid
标题
内容
创建时间
更新时间
标签
附件信息
```

---

### diary_archive_index

归档目录表。

仅记录：

```text
归档文件位置
归档时间范围
文章数量
文件大小
SHA256
```

例如：

```text
2020-2021.diarybak
2022-2023.diarybak
```

方便快速定位历史归档。

---

# 三、归档方案

## 主格式：.diarybak

采用：

```text
ZIP
+
JSON
+
附件目录
```

结构：

```text
2020-2021.diarybak
│
├── manifest.json
├── entries.json
└── attachments
    ├── img001.jpg
    ├── pdf001.pdf
    └── ...
```

---

### manifest.json

记录：

```json
{
  "version": "1.0",
  "archive_uuid": "A001",
  "start_date": "2020-01-01",
  "end_date": "2021-12-31",
  "entry_count": 856
}
```

---

### entries.json

记录全部日记数据：

```json
[
  {
    "uuid": "...",
    "date": "...",
    "title": "...",
    "content": "...",
    "tags": ["专利","学习"]
  }
]
```

---

### 附件目录

保存：

```text
图片
PDF
录音
视频
```

保证完整恢复。

---

# 四、导入方案

采用：

```text
UUID唯一判定
```

数据库主键：

```sql
id INTEGER AUTOINCREMENT
```

仅供数据库内部使用。

真正业务主键：

```sql
uuid TEXT UNIQUE
```

导入时：

```sql
INSERT OR IGNORE
```

判断依据：

```text
uuid
```

不是：

```text
标题
时间
内容
```

这样跨设备恢复不会产生重复数据。

---

# 五、历史查阅方案

核心组件：

```text
ArchiveReader
```

---

不再采用：

```text
导入临时表
```

方式。

而是：

```text
直接读取 .diarybak
```

流程：

```text
点击归档
↓
打开ZIP
↓
读取entries.json
↓
内存显示
```

特点：

```text
零导入
零写库
零污染
```

退出后：

```text
释放内存
```

即可。

---

### ArchiveReader支持

```text
浏览
搜索
标签筛选
时间筛选
导出
```

用户体验上与普通日记无差别。

---

# 六、归档策略

建议：

```text
手机仅保留近5年
```

例如：

```text
2026年
```

数据库保留：

```text
2022~2026
```

更早数据：

```text
2021及以前
```

归档为：

```text
2020-2021.diarybak
```

然后从 SQLite 中物理删除。

这样：

```text
数据库体积长期稳定
```

性能恒定。

---

# 七、专项导出方案

采用：

```text
标签
+
关键词
```

双层筛选。

---

第一层：

```text
精准标签匹配
```

例如：

```text
#专利
```

---

第二层：

```text
关键词兜底
```

例如：

```text
专利
发明
创新
```

避免漏掉未打标签内容。

---

导出结果：

```text
专利.diarybak
```

或者：

```text
专利知识库.md
```

独立保存。

---

# 八、Markdown方案

定位：

```text
纯阅读格式
```

结构：

```text
Diary
│
├── 2026
├── 2025
├── 2024
└── ...
```

文件：

```markdown
---
date: 2026-06-01
tags:
  - 专利
  - 学习
---

今天完成了……
```

作用：

```text
电脑直接阅读
Typora阅读
Obsidian阅读
Git备份
```

---

不承担：

```text
重新导入App
```

职责。

唯一恢复格式仍然是：

```text
.diarybak
```

避免用户修改 Markdown 后造成恢复失败。

---

# 九、归档完整性验证

增加组件：

```text
ArchiveValidator
```

功能：

```text
验证归档是否损坏
```

流程：

```text
读取manifest
↓
检查entries
↓
检查附件
↓
校验SHA256
↓
输出报告
```

结果：

```text
√ entries.json正常

√ 856篇日记完整

√ 245个附件完整

√ SHA256校验通过

归档完整
```

适合长期保存场景。

---

# 十、最终架构图

```text
个人日记 App

SQLite
│
├─ diary
│      （近5年活跃数据）
│
├─ diary_archive_index
│      （归档目录）
│
├─ Exporter
│      ↓
│   .diarybak
│
├─ Importer
│
├─ ArchiveReader
│      （直接读取归档）
│
├─ ArchiveValidator
│      （验证归档）
│
└─ Markdown Export
       （电脑阅读）
```

## 最终设计原则

归纳成一句话：

> **SQLite负责高效使用，.diarybak负责永久保存，ArchiveReader负责历史查阅，Markdown负责通用阅读。**

这样既保证了长期数据安全，又保证了手机端始终轻量流畅，同时未来扩展到电脑工具、云备份、多设备同步时也不会推翻现有架构。
